# Техническое задание на проверку и доработку сервиса EventGo

**Источник требований:** хакатон «EventTech: сервис для организации мероприятий»  
**Проверяемый продукт:** локальный веб-сервис EventGo в папке проекта  
**Назначение документа:** единый чеклист для аудита уже существующего сайта и план доработок  
**Версия продукта на момент составления:** 1.4 (Node.js + SQLite, без внешних npm-зависимостей)  
**Язык интерфейса:** русский

Этот документ фиксирует:

1. Что сервис **обязан** уметь по исходному ТЗ хакатона EventTech.

## 2. Продукт и проблема

### 2.1. Продукт

Цифровой сервис для подготовки и проведения мероприятий: создание события, план задач, команда и подрядчики, бюджет, регистрация гостей, контроль подготовки и базовая аналитика.

### 2.2. Целевая аудитория

| Аудитория | Как используется в EventGo |
| --- | --- |
| Организаторы деловых/корпоративных событий | Роль `organizer` |
| Ивент-агентства, команды конференций/форумов/хакатонов | То же + демо-события |
| Участники оргкоманды | Роль `member` |
| Гости мероприятия | Публичная афиша, регистрация, билет с QR |

### 2.3. Проблема, которую решаем

Сейчас подготовку обычно ведут в таблицах, мессенджерах, почте и отдельных сервисах регистрации. EventGo должен собрать ключевые процессы в одном пространстве: задачи, команда, бюджет, гости, контроль готовности.

### 2.4. Границы прототипа

- Локальный запуск без интернета (кроме опционального ИИ).
- Демонстрационные аккаунты, без публичной регистрации организаторов.
- Без реальной почтовой рассылки и оплаты.
- Без обязательной интеграции с внешними календарями.

## 3. Роли и права доступа

| Роль | Кто в системе | Обязательные права | Запреты |
| --- | --- | --- | --- |
| Администратор мероприятия (организатор) | `organizer@eventgo.local` | CRUD событий, задачи, команда, бюджет, гости, аналитика, проверка билетов, файлы, чат, ИИ | — |
| Участник оргкоманды | `team@eventgo.local` | Свои события, смена статуса своих задач, комментарии, файлы, чат, ИИ (без финансов) | Бюджет, суммы подрядчиков, аналитика |
| Участник мероприятия (гость) | без пароля: `/afisha`, `/register/...`, `/my-tickets` | Афиша, регистрация, просмотр билета/QR | Рабочие разделы команды |

### Критерии проверки ролей

- [ ] Организатор входит и видит все разделы навигации.
- [ ] Участник команды не видит «Бюджет» и «Аналитика» в меню.
- [ ] API не отдаёт участнику финансовые поля (даже при прямом запросе).
- [ ] Гость без входа открывает афишу и регистрируется по ссылке.
- [ ] Гость не читает и не пишет в чат команды.

## 4. Обязательные функциональные требования (MVP хакатона)

Статусы при проверке: **Есть** / **Частично** / **Нет** / **Сверх ТЗ**.

### 4.1. Создание и управление мероприятием

| ID | Требование | Как проверить | Ожидаемый результат |
| --- | --- | --- | --- |
| E-01 | Создать мероприятие | Организатор → «Мероприятия» → «Создать событие» | Событие появляется в списке и сохраняется после перезагрузки |
| E-02 | Название | Поле «Название» | Обязательное, отображается в карточке и дашборде |
| E-03 | Тип мероприятия | Выбор типа | Форум / Конференция / Встреча / Хакатон / Фестиваль / Корпоративное / Другое |
| E-04 | Дата и время | Datetime | Сохраняется, показывается в обзоре и афише (Якутск UTC+9) |
| E-05 | Место или онлайн-ссылка | Поле «Место или ссылка» | Сохраняется и видно гостю |
| E-06 | Описание и цели | Поля description / goal | Редактируются, видны в карточке/гостевой странице |
| E-07 | Планируемое число участников | capacity | Лимит регистраций; нельзя зарегистрировать сверх лимита |
| E-08 | Бюджет | Число ≥ 0 | Участвует в расчётах остатка и алертов |
| E-09 | Ответственный организатор | owner / роль organizer | Организатор владеет и управляет событием |
| E-10 | Список оргкоманды | Раздел «Команда» | Можно добавить людей с ролями |
| E-11 | Редактирование параметров | Иконка редактирования | Изменения сохраняются |
| E-12 | Статус события | planning / active / finished | Фильтры списка и афиша учитывают статус |
| E-13 | Удаление события | Действие удаления | Событие и связанные данные удаляются согласованно |

**Сценарий приёмки:** создать → заполнить все поля → сохранить → обновить страницу → отредактировать → снова проверить сохранение.

## 15. Итог для дальнейшей работы

1. Сначала проводим аудит по этому ТЗ и заполняем статусы ID.
2. Чиним только P0/P1, найденные аудитом.
3. Затем выбираем из P2 функции, которые усиливают защиту (опросы, каталог, напоминания).
4. Любая новая фича добавляется в таблицы этого документа с ID и критерием приёмки.

**Главный принцип (из исходного ТЗ):** побеждает не самая сложная технология, а решение, которое лучше убирает реальные проблемы организатора мероприятий.
